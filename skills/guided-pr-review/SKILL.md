# guided-pr-review

ユーザーがレビュアーとして PR を理解し、指摘を決めて投稿するまでを伴走する。
判断（どの点を指摘するか、どう書くか、投稿するか）はユーザーが行う。エージェントは材料を揃え、文面を提案する。

## 進め方の原則

- 既定では、1 回の応答で扱うフェーズは 1 つ。各フェーズの終わりで止まり、次に選べることを 1〜2 行で示してユーザーの選択を待つ。
- ユーザーが複数のフェーズをまとめて指示した場合（例: 「文面を作って投稿まで」）は、指示された範囲まで続けて進めてよい。投稿の指示もこれに含まれる。指示された範囲を超えて先回りしない。
- 秘密情報（`.env` の中身、トークン）は読まない、書かない、投稿しない。
- バックグラウンドで走らせた調査の結果が後から届いたら、前の整理が変わるかどうかだけを短く伝える。

## ホスティングサービス固有の操作

PR の特定、PR 用 ref の fetch、既存コメントの取得、コメントの投稿は、サービスごとにコマンドが違う。
これらが必要になったら `references/hosting.md` を読む。GitHub / Azure DevOps / GitLab の例と、それ以外のサービスで代わりに確かめることをまとめてある。
そのサービス向けの skill（例: `azure-devops-pr`）が使える環境では、そちらの手順を優先する。

## Phase 1: PR の全体像と精査候補

### 1-1. 対象 PR を特定する

- 引数に PR 番号か URL があればそれを使う。無ければ、現在のブランチを source とする open な PR を探す。
- PR のメタデータから次を控える。以降はローカルのブランチではなく、これらを基準にする。
  - source の最新 commit SHA（以下、PR SHA）
  - target ブランチ名
  - 状態（draft、マージ済みなど）と、サービスが表示する変更ファイル数

### 1-2. 正確な差分を取る

ローカルの `HEAD` やローカルの target ブランチは、PR と一致しているとは限らない（pull し忘れ、作者の force-push、fork からの PR など）。次の手順で、PR が実際に提示している差分を取る。

1. リモートから target ブランチを fetch する（`origin` は PR が属するリポジトリの remote。fork 運用では `upstream` などに読み替える）。source 側は source ブランチを fetch し、取れなければ（fork など）サービスが提供する PR 用の ref を fetch する。
2. fetch した source の commit が PR SHA と一致するか確かめる。一致しなければ PR SHA を正とし、ずれていることをユーザーに伝える。
3. 差分は `git diff origin/<target>...<PR SHA>`、履歴は `git log origin/<target>..<PR SHA>` で取る。3 点の `...` は merge-base からの差分で、サービスが表示する差分と同じ範囲になる。ローカルの `HEAD` や `<target>` は使わない。
4. 差分のファイル数が、1-1 で控えた変更ファイル数と合うか確かめる。合わなければ原因（fetch の漏れ、PR 作成後の target の進み方など）を調べてから進む。
5. ファイルを読むときは `git show <PR SHA>:<path>` を使う。ユーザーの作業ツリーを壊さないよう、許可なく checkout や reset をしない。

### 1-3. 読む

- commit message と author も読む。
- 差分は省略せずに全部読む。出力が長くて保存された場合は、そのファイルを読む。
- 差分の外も確かめる。例: 改名した識別子の旧名の残り（grep）、変更が前提にする既存の不変条件やルール、関連ドキュメント。
- 一度に読み切れない規模（目安: 変更ファイル 30 以上、または差分 2,000 行以上）では、サブエージェントへの分担を検討する。
  - ディレクトリや関心ごとで分け、各サブエージェントに PR SHA と担当範囲を渡す。
  - 変更の要約と精査候補（`path:line`、何が起きうるか、確かめたこと / 確かめていないこと）を、サブエージェント自身にファイルへ書き出させる。
  - PR の中心になる変更は、分担せずに自分で読む。

### 1-4. 既存のコメントを読む

- PR の既存スレッド（未解決・解決済みの両方）と、他のレビュアーのレビュー状況を取得する。
- 精査候補が既存スレッドと重なる場合は、「既出」として thread ID と指摘者を示す。新しいコメントではなく、既存スレッドへの返信を候補にする。
- 作者が PR の説明や返信ですでに説明している点は、その説明を踏まえたうえで候補にするかを決める。

### 1-5. ユーザーに提示する形

1. **概要**: PR、作者、commit 数、規模（ファイル数と +/− 行数）、PR SHA とローカルとのずれの有無
2. **目的**: 何を可能にする変更か（2〜3 行）
3. **ファイル別の変更内容**: 新規 / 変更 / 削除を明示する。テンプレートやコードは、中心になる仕組みを短く説明する
4. **挙動の変化（旧 → 新）の表**: 戻り値、環境変数、依存、規約の例外、方針の変更など、利用者から見て変わる点
5. **既存のコメント**: 未解決スレッドの要旨と件数（無ければ「なし」）
6. **レビューで確認したい点**: 番号付きのリスト。各項目に場所（`path:line`）、何が起きうるか、確かめたこと / 確かめていないこと、既出かどうかを書く
   - 実行や外部ソースで確かめていない前提は「未検証」と書く。推測を事実のように書かない
   - 重要度の高い順に並べ、最後に「軽微」をまとめてよい

最後に次の選択肢を示して止まる: 深掘りする点を選ぶ / コメント文面を作る / 図解を作る。
図解は Phase 4 の基準に当たる PR のときだけ選択肢に入れ、当たらなければ作らない理由を 1 行添える。

## Phase 2: 選ばれた観点の深掘り

ユーザーが番号で選んだ点だけを扱う。補足の指示（例: 「停止した後のフローの想定を聞く」）があれば、その方向で論点を組み直す。

- PR SHA 時点のコードで、該当行と前後を読み直す。行番号は、PR SHA 側（差分の新しい側）のものを確定させる
- 依存ライブラリの挙動が論点なら、可能な範囲で一次情報を確かめる（インストール済みのソース、公式ドキュメント）。確かめられなければ、そう書く
- 各点を **質問 / 提案 / 確認 / 軽微** のどれにするか決める。断定できない点は質問にする
- 1 つの点に場所の違う小項目が複数あれば、コメントを分ける

## Phase 3: コメント文面の提案と投稿

### 3-1. 文面を提案する

各コメントについて、投稿先（ファイルと行、PR 全体、または返信先の既存スレッド）と本文を示す。本文の書き方:

- PR の説明や既存のコメントで使われている言語で書く。判断できなければユーザーに確かめる
- 先頭にタグを付ける: `[質問]` `[提案]` `[確認]` `[軽微]` `[軽微・対応任意]`（英語で書く場合は `[Question]` `[Suggestion]` などに置き換える）
- 何が起きるか → なぜか → どうすればよいか（案を 1〜2 個）、の順で書く。質問では想定される選択肢を挙げ、答えやすくする
- 作者の意図を否定する断定を避け、丁寧に書く
- 本文には内部ツール名（エージェント名、エージェント向けの設定ファイル名など）を書かない。必要ならプロジェクト規約と言い換える

文面の修正指示があれば反映して、もう一度示す。投稿はユーザーの指示を受けてから行う（「進め方の原則」のとおり、最初から投稿まで指示されていればそれに従う）。

### 3-2. 投稿と確認

- 行コメントは PR SHA 側の行に付ける。サービスが commit の指定を求める場合は PR SHA を渡す
- 既存スレッドへの返信は、新しいスレッドではなく返信として投稿する
- 投稿後にスレッド一覧を取り直して、次を確かめる: 文字化けしていないこと、指定したファイルと行に付いていること、件数が合っていること
- 投票（approve / reject）は、ユーザーの指示が無い限りしない
- 結果は表で返す: 指摘番号、thread ID、場所、要旨
- 投稿できるツールが無い環境では、投稿先と本文をコピーしやすい形で渡し、ユーザーに投稿してもらう

## Phase 4: 図解（新しい概念・実装を含む PR だけ）

作る: 新しい仕組み、新しいデータフローやリクエスト経路、新しいテンプレートやモジュール群、状態の持ち方の変更、設計方針の変更。
作らない: バグ修正、文言修正、軽微なリファクタリング、依存の更新。

作るのはユーザーの同意を得てから。作るときは `references/diagramming.md` を読み、図の選び方と出力先に従う。
