# guided-pr-review

ユーザーがレビュアーとして PR を理解し、指摘を決めて投稿するまでを伴走する。
判断（どの点を指摘するか、どう書くか、投稿するか）はユーザーが行う。Claude は材料を揃え、文面を提案する。

各フェーズの終わりで一度止まり、ユーザーの選択を待つ。複数のフェーズを先回りして進めない。

## Phase 1: PR の全体像と精査候補

### 1-1. 対象 PR を特定する

- 引数に PR 番号か URL があればそれを使う。無ければ現在のブランチを source とする active な PR を探す。
  - Azure DevOps: `az repos pr list --source-branch <branch> --status active`（`azure-devops-pr` skill があれば読む）
  - GitHub: `gh pr view --json number,title,headRefOid,baseRefName`
- PR の最新 source commit とローカルの HEAD が一致するか確かめる。ずれていれば、どちらを読むかをユーザーに伝える。
- Windows では az CLI の前に `export PYTHONUTF8=1 PYTHONIOENCODING=utf-8` を付ける。一時ファイルは `/tmp` でなく `$TEMP` かスクラッチパッドに置く。

### 1-2. 読む

- `git fetch origin <base>` の後、`git log <base>..HEAD` と `git diff <base>...HEAD`。commit message と author も読む。
- 差分は省略せずに全部読む。出力が長くて保存された場合は、そのファイルを Read する。
- 差分の外も確かめる。例: 改名した識別子の旧名の残り（Grep）、変更が前提にする既存の不変条件やルール、関連ドキュメント。

### 1-3. ユーザーに提示する形

1. **概要**: PR、作者、commit 数、規模（ファイル数と +/− 行数）
2. **目的**: 何を可能にする変更か（2〜3 行）
3. **ファイル別の変更内容**: 新規 / 変更 / 削除を明示する。テンプレートやコードは、中心になる仕組みを短く説明する
4. **挙動の変化（旧 → 新）の表**: 戻り値、環境変数、依存、規約の例外、方針の変更など、利用者から見て変わる点
5. **レビューで確認したい点**: 番号付きのリスト。各項目に場所（`path:line`）、何が起きうるか、確かめたこと / 確かめていないことを書く
   - 実行や外部ソースで確かめていない前提は「未検証」と書く。推測を事実のように書かない
   - 重要度の高い順に並べ、最後に「軽微」をまとめてよい

最後に、次の選択肢を示して止まる: 深掘りする点を選ぶ / コメント文面を作る / 図解を作る。

## Phase 2: 選ばれた観点の深掘り

ユーザーが番号で選んだ点だけを扱う。補足の指示（例: 「停止した後のフローの想定を聞く」）があれば、その方向で論点を組み直す。

- source commit 時点のコードで、該当行と前後を読み直す。行番号は、投稿先の差分で表示される側（新しい側）のものを確定させる
- 依存ライブラリの挙動が論点なら、可能な範囲で一次情報を確かめる（インストール済みのソース、公式ドキュメント）。確かめられなければ、そう書く
- 各点を **質問 / 提案 / 確認 / 軽微** のどれにするか決める。断定できない点は質問にする
- 1 つの点に場所の違う小項目が複数あれば、コメントを分ける

## Phase 3: コメント文面の提案と投稿

### 3-1. 文面を提案する

各コメントについて、投稿先（ファイルと行、または PR 全体）と本文を示す。本文の書き方:

- 先頭にタグを付ける: `[質問]` `[提案]` `[確認]` `[軽微]` `[軽微・対応任意]`
- 何が起きるか → なぜか → どうすればよいか（案を 1〜2 個）、の順で書く。質問では想定される選択肢を挙げ、答えやすくする
- 作者の意図を否定する断定を避け、丁寧語で書く
- 本文には内部ツール名（CLAUDE.md、Claude など）を書かない。必要ならプロジェクト規約と言い換える

ユーザーが明示的に「投稿して」と指示するまで投稿しない。文面の修正指示があれば反映して、もう一度示す。
ただし、ユーザーが最初から投稿まで指示している場合は、作成した文面で投稿してよい。

### 3-2. 投稿と確認

- Azure DevOps: `azure-devops-pr` skill の `scripts/create_thread.sh`（`--file` と `--line` で行に付ける）か、`az devops invoke` の pullRequestThreads を使う。GitHub: `gh api` で review comment を付ける
- 投稿後に thread 一覧を GET して、次を確かめる: 文字化けしていないこと、指定したファイルと行に付いていること、件数が合っていること
- 投票（approve / reject）はユーザーの指示が無い限りしない
- 結果は表で返す: 指摘番号、thread ID、場所、要旨

## Phase 4: 図解（新しい概念・実装を含む PR だけ）

### 作るかどうか

作る: 新しい仕組み、新しいデータフローやリクエスト経路、新しいテンプレートやモジュール群、状態の持ち方の変更、設計方針の変更。
作らない: バグ修正、文言修正、軽微なリファクタリング、依存の更新。図を作らない場合は、作らない理由を 1 行で伝える。

ユーザーに頼まれていなくても、該当する PR では Phase 1 の最後に「図解を作れます」と提案する。作るのは同意を得てから。

### 作り方

- Artifact ツールが使えるなら、`action: "quickstart"` を呼び、`artifact-diagramming` skill を読んでから 1 枚の HTML ページを作る。使えなければ、スクラッチパッドに HTML を置くか、mermaid を応答に書く
- 図はそれぞれ 1 つの主張を持たせ、仕組みそのものを描く。箱に名前を並べるだけの図にしない。PR に応じて次から選ぶ:
  - **利用者から見た流れ**: シーケンス図。初回、継続、例外経路（使えない経路も含む）をフェーズ帯で分ける
  - **実装の構成**: リクエストの経路と、設定・派生値の関係。矢印にはラベルを付ける（例: 「照合」「起動時に構築」）
  - **判定ロジック**: フローチャートと、入力ごとの結果の表
  - **なぜこの設計か**: 採らなかった構成と採った構成を並べ、違いが出る辺を描く
  - **失敗に気付くタイミング**: 起動時 / 初回実行時 / 気付けない、の表
- 判定関数が中心の PR では、同じ順序で判定を再現する小さなシミュレーターを付けると理解が速い。最初から例の入力を実行済みにしておく
- 例の値（モデル名、ID など）は例と明記する。PR の記述をもとに推定した部分は、そう書く
- ページの最後に、Phase 3 で投稿した指摘（thread ID）と図のどこに当たるかの対応を載せる
- 公開後、ページは非公開で、PR の作者などに見せるには Share メニューで共有が必要と伝える
- 描画を自分で確認していなければ、そう伝える

## 進め方の注意

- 1 回の応答で扱うフェーズは 1 つ。各フェーズの最後に、次に選べることを 1〜2 行で示す
- 秘密情報（`.env` の中身、トークン）は読まない、書かない、投稿しない
- バックグラウンドで走らせた調査の結果が後から届いたら、前の整理が変わるかどうかだけを短く伝える
