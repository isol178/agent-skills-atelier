# 証拠のカタログ

SKILL.md §4〜§6 の補足。成果物ごとに「何の正典になりやすいか」「どう古くなるか」を知っておくと、証拠の重み付けがぶれにくい。

## 成果物の種類ごとの性質

原則：**検査の仕組みがある成果物ほど、黙って古くならない**。CI で実行されるテスト、型、スキーマ、migration はずれると落ちる。誰も検査しない what コメントと文書は、静かに古くなる。逆に、検査の仕組みがあるのに乖離が残っているなら、その検査が止まっている（skip、CI 対象外、生成の手順漏れ）ことを疑う。

| 成果物 | 何の正典になりやすいか | 古くなり方 | 読むときの注意 |
|---|---|---|---|
| CI で実行されるテスト | 期待される挙動 | 古くはならないが、実装に合わせて書き換えられうる | 期待値がいつ・どのコミットで入ったか。実装の変更と同じコミットで書き換えられていれば独立した証拠ではない |
| skip されたテスト、xfail | 既知の乖離 | 放置される | 乖離が認識済みである証拠。skip の理由を読む |
| 型定義・スキーマ・migration | データの形 | 強制されるので古くならない | migration はスキーマの履歴の正典。スキーマを説明した文書は遅れがち |
| 生成物（OpenAPI、クライアント、API リファレンス） | なし（生成元の写し） | 再生成忘れ | 生成元に遡る。生成物を独立した証人として数えない |
| 公開済みの API 文書・外部との契約 | 外部への約束 | 実装の変更に取り残される | 公開した時点で約束なので、§7 の収束で重い。公開日と変更履歴を確認する |
| ADR | 決定とその理由 | status の更新漏れ（superseded にされていない） | 後続の ADR や、ADR 以後の大きな変更がないか確認する |
| 設計書・仕様書 | 書かれた時点の意図 | 実装後に急速に古くなる | 実装より先に書かれた目標か、実装後の現状説明かで意味が変わる |
| README・Wiki・運用手順書 | 利用方法・運用の前提 | 古くなりやすい | 版履歴があれば §3 と同じ問いで調べる |
| why コメント（理由を書いたもの） | 局所的な意図・制約 | 比較的古くなりにくい | 理由そのものが Chesterton's fence の答えになる。理由の前提がまだ有効かは確認する |
| what コメント（処理内容を書いたもの） | 書かれた時点の実装 | 最も早く古くなる（誰も検査しない） | 書かれた時点で真だったかを確かめる。コピーされたコメントに注意 |
| TODO / FIXME / HACK | 既知の乖離・暫定対応 | 放置される | 乖離が認識済みである証拠。暫定対応が恒久化していないか |
| コミットメッセージ・PR・issue | その時点の意図 | 変わらない（日時付きの記録） | squash では意図が混ざる。issue の結論とコミットの内容が一致しているか |
| CHANGELOG・リリースノート | 利用者に告知した変更 | 書き忘れ | 告知された変更は意図的。告知がないことは「意図的でない」証拠としては弱い |
| 呼び出し側のコード | 契約の解釈 | 呼び出される側の変更に追随しないことがある | 別の作者・別の時期に書かれたものは独立した証人。回避策のコメントは特に有力 |
| 本番の挙動・保存済みデータ | 事実上の契約 | — | 依存の証拠（§7 の収束に効く）。参照は読み取りのみ、権限の範囲で、ユーザーの了承を得て |

## 証拠の強さの目安

| 強さ | 例 |
|---|---|
| 決定的 | プロジェクトが宣言した正典、外部の権威（規格・契約・外部 API 仕様）、挙動の変更を明言したコミット・issue・CHANGELOG、その挙動を求める ADR や障害報告（postmortem）の対応項目、乖離を認めて方針を決めた PR のレビュー議論 |
| 強 | 乖離点のコミットが挙動不変を名乗っているのに挙動が変わっている／書かれた時点では真だった記述と、その後の片側だけの変更／別の作者・別の時期の呼び出し側が一方を前提にしている／機能と同時に書かれた、挙動を名前に含むテスト／理由を書いた why コメント・ADR |
| 中 | 周辺の流儀（兄弟の実装）との一致・不一致／移行の向き／内部の論理（単位・他の制約との整合）／関連する issue があるが結論が明記されていない |
| 弱 | 乖離点のコミットで一緒に書き換えられたテスト／コピペされた記述／作者の一般的な傾向／理由が見つからないこと |
| 判別力なし | どちらが新しいか、どちらが詳しいか、どちらが丁寧に書かれているか、どちらがきれいな設計か |

「判別力なし」に挙げたものは、主張の真偽についての証拠ではない。最後の「どちらがきれいな設計か」は、§7 で収束先を選ぶときにだけ使う。

## 依存の調べ方

- **リポジトリ内**: 関数名・エンドポイント・エラーコード・フィールド名で grep し、呼び出し側が何を前提にしているかを1件ずつ確かめる。数を数えるより、前提の内容を読む
- **同じ組織の他のリポジトリ**: アクセスできるなら、クライアント・SDK・他のサービスを検索する。できないなら「外部の利用者は未確認」と報告に書く
- **公開範囲**: エンドポイントやライブラリ関数が外部に公開されているか（公開 API の一覧、ルーティング、`__all__`、export、ドキュメントサイト）。公開されていれば外部の依存がある前提で扱う
- **データ**: 保存済みのデータが一方の形式を前提にしていないか（enum の値、日付の形式、単位）。値の分布を見る必要があれば、読み取りのみのクエリを、権限の範囲でユーザーの了承を得て実行する

## 移行の向きの測り方

多数派と少数派が割れているとき、どちらが目標かは数ではなく向きで決まる。

```bash
# 新旧それぞれのパターンが最初に現れたコミット
git log -S '<新パターン>' --reverse --format='%h %as %s' | head -3
git log -S '<旧パターン>' --reverse --format='%h %as %s' | head -3

# 2つの時点での出現数の比較（増えている方が目標であることが多い）
for rev in $(git rev-list -1 --before='1 year ago' HEAD) HEAD; do
  echo "$rev new=$(git grep -c '<新パターン>' $rev | awk -F: '{s+=$NF} END {print s+0}') \
old=$(git grep -c '<旧パターン>' $rev | awk -F: '{s+=$NF} END {print s+0}')"
done

# 最近追加・変更されたファイルがどちらを使っているか
git log --since='6 months ago' --diff-filter=AM --name-only --format= | sort -u | xargs grep -l '<新パターン>' 2>/dev/null
```

移行を決めた ADR・issue・計画書があれば、それが決定的な証拠になる。
