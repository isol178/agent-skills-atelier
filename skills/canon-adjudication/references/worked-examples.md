# 判定の実例

SKILL.md の手順を通した判定の例。どれも「最初に思いつく判定」が外れる、または不完全になる形を選んである。

## 例1: drift — 理由付きの変更と、取り残されたコメント

- **乖離**: `price_cache.py` のコメント「価格は 5 分キャッシュする」に対し、実装は `TTL_SECONDS = 60`
- **調べたこと**: スクリプトの Timeline で、コメントと定数を最後に同時に変えたのは導入時のコミット。その後、定数だけが `perf: shorten price cache TTL to 60s to reduce stale prices (#311)` で変わっている。issue #311 には「古い価格での注文が週に数件」とあり、CHANGELOG にも記載がある
- **判定**: H-impl（確信度: 高）。挙動の変更を明言したコミット・issue・CHANGELOG という決定的な証拠がある
- **収束**: コメントを直し、#311 を参照する。同じコミットの差分を見ると README の「価格は最大 5 分遅れる」も取り残されていたので、同じ根の乖離として一緒に直す

## 例2: regression — マージ衝突の解消で消えた処理

- **乖離**: 設計書「パスワードリセットのトークンは一度使うと無効になる」に対し、実装は使用後もトークンを無効化しない
- **最初に思いつく判定**: 実装の方が新しいので設計書が古い → 誤り
- **調べたこと**: 機能追加のコミットでは設計書と `token.invalidate()` が同時に入っている（書かれた時点で真）。`trace_divergence.py` で、その後に実装だけを変えたのはマージコミット1件だと分かる。`git show --remerge-diff` で見ると、別ブランチの refactor との衝突を解消した際に `token.invalidate()` の行が落ちている。マージの件名と PR に挙動を変える意図の記述はない
- **判定**: H-doc（確信度: 高）。挙動を変える意図のない変更で挙動が変わっており、書かれた時点では真だった
- **収束**: 認証に関わるので深さは慎重。使い回せるトークンに正当な依存はないことを確認したうえで、単回使用を検証するテストを先に書いて実装を直す。マージ衝突の解消が原因だったことを PR に書く

## 例3: 移行中の少数派 — 多数派が古い側

- **乖離**: `events.created_at()` の docstring「タイムゾーン付き（UTC）の datetime を返す」に対し、実装はタイムゾーンなしの datetime を返す。コードベースの約 7 割はタイムゾーンなしで扱っている
- **最初に思いつく判定**: 多数派に合わせて docstring を直す → 誤り
- **調べたこと**: ADR-0012「すべての日時をタイムゾーン付き UTC で扱う」（accepted）がある。`git log -S` で見ると、タイムゾーン付きのパターンは ADR 以後に現れて増え続けており、直近半年に追加されたモジュールはすべてそちらを使っている。この docstring は ADR の移行チケットで先に書き換えられ、実装の移行が未完了
- **判定**: H-plan（確信度: 高）。docstring は目標としての正典で、現状の説明としては誤り
- **収束**: docstring をタイムゾーンなしに戻すことはしない（目標の記録が消える）。実装の移行は単発の修正ではなく移行チケットの範囲で行う。呼び出し側でタイムゾーンの有無を混ぜて比較している箇所があると TypeError になるので、その一覧を報告に添える。それまでの間、docstring に「移行中。現状はタイムゾーンなし」と注記する案を出す

## 例4: 依存のある逸脱 — 意図と収束先が分かれる

- **乖離**: CLI の文書「入力の検証エラーでは終了コード 1」に対し、実装は 2 を返す
- **調べたこと**: 2年前の `refactor: centralize error handling` で 1 から 2 に変わっている。挙動の変更に触れた記述はなく、当時のテストは同じコミットで期待値を書き換えている（独立した証拠ではない）。一方、社内の別リポジトリの CI スクリプト3本が `if [ $? -eq 2 ]` で検証エラーを判定している
- **判定**: 意図については H-doc（確信度: 中〜高）。リファクタリングでの事故である
- **収束**: 意図どおり 1 に戻すと、2 に依存している CI スクリプトが壊れる。2年間公開されてきた挙動なので、「2 を新しい正典として文書を直す」か「非推奨期間を設けて 1 に戻す」かをユーザーに判断してもらう。推奨は前者（依存の実害が大きく、1 に戻す利点が小さい）とし、判断が出るまでどちらも書き換えない

## 例5: 見かけの乖離 — 条件が違うだけ

- **乖離**: README「タイムアウトの既定値は 30 秒」に対し、コードは `DEFAULT_TIMEOUT = 10`
- **調べたこと**: §1-3 で実効設定を追うと、`config/production.yaml` が 30 を設定している。README は運用中のサービスについての文書で、コードの定数はライブラリとして使われたときの既定値。両者はそれぞれ正しい
- **判定**: 見かけの乖離（条件の違い）
- **収束**: どちらも書き換えない。README に「本番設定では 30 秒。設定がない場合の既定値は 10 秒」と条件を書き足す提案をする
