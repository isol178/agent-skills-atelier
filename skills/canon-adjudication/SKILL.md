# canon-adjudication — 乖離したとき、どれが正典かを推定する

文書とコードの乖離に気づいたエージェントが最もやりがちな失敗は、確かめずに「動いているのだからコードが正しい」と文書を書き換えることだ。乖離の原因が実装の事故なら、これはバグを仕様として追認し、しかも事故の唯一の証拠（元の記述）を消す。逆向きの「文書が正しいのでコードを直す」は、誰かが依存している挙動を壊す。このスキルは印象ではなく、**仮説を区別できる証拠**で判定する。

## 前提：3つの問いを混ぜない

「どれが正典か」は、性質の違う3つの問いが混ざったものである。

1. **今どう動くか**（事実） — 実際に実行されるコードと実効設定が答え。推定ではなく観測で確定する（§1）
2. **本来どう意図されていたか**（推定） — このスキルの中心（§2〜§6）。証拠から推定し、確信度を付ける
3. **どこに収束させるか**（裁定） — 通常は 2 の答えに合わせる。ただし依存・設計の良し悪し・外部要件の変化で 2 とずれることがある（§7）

設計の良し悪しは 3 でだけ使い、**2 の証拠には使わない**。「きれいな方が意図だったはず」は推定ではなく願望で、不格好な実装に隠れた制約を消す最短経路になる。

## 0. 深さを決める

全ステップを常に踏む必要はない。最初に、どこまで調べるかを決める。

| 深さ | 該当するもの | やること |
|---|---|---|
| 軽 | 挙動に影響しない記述（内部関数のコメント、言い回し）、または宣言された正典がそのまま答えを出す | §1 → §2 → §3 の手順 2〜3 を1回 → 短縮版の判定カード |
| 標準 | 内部の挙動・内部 API・テストに影響する | §1〜§8 を簡潔に |
| 慎重 | 公開 API・外部との契約、永続データの形式、認証・認可・金額・個人情報、または収束させると誰かが依存している挙動が変わりうる | 標準に加えて §4 の依存を広く調べ、挙動を変える修正の前にユーザーに確認する。広く調べるとは、この挙動に依存しうる相手（呼び出し側のコード、外部の利用者や他のサービス、メールの受信者や運用担当のような人）を列挙し、手の届く範囲で確かめること。リポジトリ内の呼び出し側はすべて見る。リポジトリの外は、アクセスできる手段があれば確かめ、なければ「未確認」と書く |

- 収束の向きはまだ分からないので、深さは最初に、ありうる収束のうち影響が最も大きいもので決める。§6 で向きが決まり、変わるのが文書・コメントだけと分かったら、§7 の行動はそれに合わせてよい（調査をやり直す必要はない）
- 別のタスクの途中で見つけた乖離が、そのタスクの完了を妨げないなら、軽で判定して報告し、本来のタスクに戻る。範囲外の修正を勝手に広げない
- 調査の途中で、同じ根ではない別の乖離に気づいたときも同じ扱いにする（軽で判定し、報告だけして直さない）。本題の判定に関わるなら、本題の判定カードの「反証・未確認」にも書く
- 対象は、文書・コメント・テスト・実装のあいだの乖離である。実装と外部の規格とのずれのように、成果物どうしの食い違いではない問題に気づいたら、1行で報告するだけにする

## 1. 主張を分解し、乖離が実在するか確かめる

### 1-1. 対立する主張を引用で並べる

各側の記述を、原文の引用と `path:line` で並べる。

- 「この文書は古い」のような文書単位の判定はしない。**正典かどうかは主張ごとに決まる**。乖離を原子的な主張に分ける（例：存在しない ID への GET のステータス、ID の形式、既定のタイムアウト値）。同じ文書の中で節 A は正しく節 B は古い、は普通に起きる
- 同じ主張を述べている他の場所も探して並べる（識別子・定数・エラーコード・特徴的な語句で grep）。別の文書、コメント、テスト、型・スキーマ、OpenAPI、クライアントコード、CHANGELOG、UI の文言。これらは §4〜§5 で証人として使う

### 1-2. 見かけの乖離を除外する

次のいずれかなら矛盾ではない。類型を「見かけの乖離」として、文書側に条件を書き足す提案で終える。

- **抽象度の違い**: 文書は保証（契約）を、コードはその範囲内のより強い実装を書いている（文書「順序は保証しない」、コード「常に昇順」）
- **版の違い**: 文書が別のリリース・API バージョン・ブランチを説明している
- **条件の違い**: feature flag・設定値・環境・テナント・ロケールで分岐し、両者が別の条件を書いている
- **単位・用語の違い**: 秒とミリ秒、同じ概念の別名
- **読んだコードが実行されていない**: dead code、設定や環境変数での上書き、DI での差し替え、古い生成物、ミドルウェアでの変換

### 1-3. 実効挙動を観測で確定する

コードを読んで「こう動くはず」で済ませない。安く実行できるなら実行する（既存テスト・REPL・curl・小さなスクリプト）。テストランナーなどが入っていなければ、勝手にインストールせず、同じ検査を小さなスクリプトで行う（インストールが要るならユーザーに確認する）。観測用のスクリプトはインラインで実行し、リポジトリにファイルやキャッシュ（`__pycache__` 等）を残さない。既定値は定数だけでなく、実際に使われる設定（設定ファイル・環境変数・デプロイ設定）まで追う。記録は観測と推測を分ける。

```
observed: pytest tests/test_users.py::test_missing で 400 が返ることを確認
inferred: 本番も同じ分岐を通るはず（本番設定との差分は未確認）
```

## 2. 宣言された正典を確認する

明示された取り決めは推論に勝つ。ここで答えが出れば、以降は短縮してよい。

- **プロジェクトの宣言**: CLAUDE.md / AGENTS.md / CONTRIBUTING / README、文書冒頭の「〜が正」「このファイルは自動生成。編集禁止」。「詳しくは docs/X を参照」のような置き場所の案内は、正典の宣言ではない
- **生成の向き**: コードから文書を生成しているか（アノテーション → OpenAPI、docstring → API リファレンス）、文書からコードを生成しているか（スキーマ駆動、protobuf、OpenAPI generator）。生成物は独立した証人ではないので、生成元まで遡る。生成物と生成元のずれは裁定ではなく再生成の問題
- **外部の権威**: RFC などの規格、外部サービスの API 仕様、法令、顧客との契約、公開済みの API 文書（公開した時点で外部への約束になる）。外部の権威に反している側は、文書でもコードでも誤り。公開済みとは、外部の利用者に向けて配布・掲載されていること（ドキュメントサイト、パートナーへの提供物、配布した SDK の文書）。リポジトリ内にあるだけの文書は、公開されているかを確かめてから扱い、確かめられなければ決定的な証拠にはしない
- **ADR**: accepted で、superseded になっていないもの

ただし宣言そのものが死んでいる兆候（「仕様書が正」とあるのに仕様書は2年更新されておらず、その間にコードは何百回も変わっている等）があれば絶対視せず、その事実を報告に含める。

## 3. 来歴：乖離を生んだ変更の意図を読む

「新しい方が正しい」は判定に使えない。コードの方が新しいという事実は、「コードを意図して変え、文書の更新を忘れた（文書が古い）」とも「リファクタリングでコードを壊した（文書が正しい）」とも両立する。2つを分けるのは時刻ではなく、乖離を生んだ変更の意図である。問いは次の1つに絞る。

> 最後に、もう一方の存在を知った上で変更したのはどちらか。その変更は挙動を変えるつもりだったか。

### 手順

1. **履歴が使えるか確かめる**: `git rev-parse --is-shallow-repository` が true なら履歴が途中で切れている。`git fetch --unshallow` を試し、できなければ来歴の証拠は弱く扱う。`git status` と `git log <base>..HEAD` で、乖離がこのブランチや作業中の変更で生じていないかも見る

2. **タイムラインを作る**: 同梱スクリプトで、各主張の場所の履歴を1本に並べる。`<skill-dir>` はこの SKILL.md があるディレクトリ。リポジトリ内で実行し、パスはリポジトリルートからの相対で渡す。

   ```bash
   python <skill-dir>/scripts/trace_divergence.py \
     doc=docs/api.md:40-52 code=src/users.py::get_user test=tests/test_users.py \
     -G 'MAX_RETRIES\s*='
   ```

   アンカーは `path:開始-終了`（行範囲）、`path::関数名`、`path`（ファイル全体）の3形式で、2つ以上渡す。主張が書かれた行そのものを指すように選ぶ。docstring やコメントの主張は行範囲で指定する（`::関数名` は関数のどこが変わっても変更扱いになるので、実装の挙動を表すアンカーに使う）。最初の2つには対立する主張を置き、証人（テスト、呼び出し側）は3つ目以降に足す（Read first は最初の2つの組から作られる）。値の変更（3 → 5）は `-G 正規表現`、識別子の追加・削除は `-S 文字列` で追う。出力の読み方：

   - Timeline: どれかのアンカーを変えたコミットだけが並ぶ（どのアンカーにも触れないコミットは出ない）。`X` = そのアンカーを変更、`f` = そのコミットがこのアンカーと同じファイルの別の場所を変更、`.` = 触れていない
   - Pairs: `last changed together in` = 両者を同じコミットで変えた最後の時点で、`only … moved since then` = その後に片側だけを動かしたコミット。`never changed together` なら、後から現れた側が登場したコミットが乖離の始まりの候補（仕様が先に書かれ、実装が後から書かれた場合など）
   - タグ: `[no-behavior-change?]` は件名が挙動不変を名乗るコミット、`[mass: N files]` と `[blame-ignore-revs]` は整形などの一括変更
   - True-when-written checks: 手順 4 でそのまま使うコマンド
   - Read first: 乖離が始まりえたコミット。まずこれを `git show` で読む

   スクリプトが使えない場合（Git 以外の版管理、文書が Wiki にある等）は、同じ問いを `git log -L`、`git log --follow`、`git log -S` / `-G`、Wiki の版履歴で調べる。コマンドの詳細は `references/git-forensics.md`。

3. **乖離点のコミットを読む**: 片側だけが動いたコミットを `git show` で読み、メッセージ・差分・関連する PR / issue から意図を分類する。

   | 片側だけを動かしたコミット | 示唆すること |
   |---|---|
   | 挙動を変える意図がある（メッセージ・issue・CHANGELOG で明言、テストの期待値を意図して更新） | 動かなかった側が古い（drift）。動いた側が正典 |
   | 挙動を変える意図がない（refactor・rename・format・依存更新・マージ衝突の解消・一括置換・no behavior change）のに挙動が変わっている | 動いた側の事故（regression）。動かなかった側が正典 |
   | 文書だけが「これからこうする」と先行した（設計・仕様の PR、チケット、TODO） | 未実装の目標。文書は目標としては正典だが、現状の説明としては誤り。両方を報告する |
   | 文書を現状の説明として直したが、コードがその通りだったことは一度もない | 文書の書き手の誤読。実装側が正典の可能性が高い |

   乖離点のコミット（片側だけを動かしたコミット）が、相手のファイルの別の場所は直したのに、この箇所は直していない（Timeline の `f`）なら、文書の存在を知りつつ見落とした drift の典型である。乖離と無関係なコミットが相手のファイルを触っただけの `f` は証拠にならない。

4. **書かれた時点で真だったかを確かめる**: 片側の現在の文言が書かれたコミットで、もう片側がどうだったかを `git show <sha>:<path>` で見る（True-when-written checks がコマンドを出す）。
   - 書かれた時点では真だった → その後にもう片側が動いた。手順 3 の表でその変更の意図を見る
   - 書かれた時点ですでに偽だった → 「最初から誤った記述」か「先に書かれた仕様から、実装が初日から逸脱した」のどちらか。実装の PR・レビューに逸脱の理由があれば意図的な逸脱。理由がなく、テストや呼び出し側が記述どおりを前提にしているなら初日からのバグ

`git blame` の1行だけで判断しない。整形・ファイル移動・一括置換のコミットが最終変更に見えているだけのことが多い（回避策は references を参照）。

## 4. 依存：誰がどちらを前提にしているか

元の作者以外が、別の時期に書いたものは独立した証人になる。

- **テスト**: どちらの挙動を期待しているかを見たら、その期待値がどう入ったかまで確かめる。機能と一緒に、挙動を名前に含むテスト（`test_returns_404_when_missing`）として書かれたなら強い証拠。乖離を生んだのと同じコミットで「fix tests」「update snapshots」として書き換えられたなら、実装に合わせて曲げられたもので独立した証拠にならない
- **呼び出し側**: 呼び出し元を grep し、何を前提にしているかを見る（文書が約束する例外を catch している、None を扱っている、404 を判定している）。実装の挙動への回避策（「文書では 404 だが実際は 400 が返る」というコメント等）は、実装の挙動がバグとして認識されていることと、それに誰かが依存していることの両方を示す
- **外部の利用者**: 公開 API、SDK、他のサービス、保存済みデータの形式、ログやダッシュボード。観測できる挙動は、文書に書かれていなくても誰かが依存している（Hyrum の法則）。これは主に §7 の収束方針に効く

本番のデータやログを見る必要があるときは、読み取りのみで、権限の範囲内で、ユーザーの了承を得てから行う。

## 5. 全体との整合と、理由の記録

### 整合

- **周辺の流儀**: 兄弟（他のエンドポイント、同種のモジュール、同じ文書の他の節）はどちらの形か。1か所だけの外れ値は事故であることが多い
- **証人は独立性で数える**: コピペされた文章、生成物、同じコミットで一緒に書かれたものはまとめて1票
- **多数派は正典とは限らない**: 移行途中のコードベースでは、古いパターンが多数派で、目標の新しいパターンが少数派になる。数ではなく向きを見る。最近書かれたコードはどちらを使っているか、どちらが増えているか、移行を決めた ADR・issue はあるか
- **内部の論理**: 単位として不自然（タイムアウト 30000 秒）、他の制約と矛盾する（リトライの合計時間がリクエストのタイムアウトを超える）

### 理由

- ADR、設計書の決定記録、PR の説明とレビューでの議論、issue、障害報告（postmortem）、CHANGELOG・リリースノートを探す。コミットから PR を引く方法は `references/git-forensics.md`
- 理由を書いた **why コメント**（「意図的に〜」「〜のため」「HACK」「workaround」「see #123」）は、処理内容を説明しただけの what コメントより信頼できる。what コメントは誰も検査しないので最も早く古くなる
- **Chesterton's fence**: 不格好な側・不自然に見える側を誤りと判定する前に、その理由を探す。理由が見つかれば意図的である。見つからないことは「理由がない」証拠としては弱い（記録されなかっただけかもしれない）

成果物の種類ごとの信頼できる範囲と古くなり方は `references/evidence-catalog.md` にまとめてある。

## 6. 競合仮説で判定する

仮説を並べ、各証拠がどの仮説と両立し、どれと矛盾するかを台帳にする。

- **H-impl**: 実装が意図どおり。文書・コメントが古いか、最初から誤り
- **H-doc**: 文書・コメントが意図どおり。実装が逸脱した（regression、初日からのバグ）
- **H-plan**: 文書は未実装の目標（計画中・移行中）。実装はまだ旧状態
- **H-neither**: 外部要件の変化などで両方とも古い。新しい決定が必要

例（文書は 404、実装は 400 を返す場合）：

| 証拠 | 強さ | H-impl | H-doc | H-plan |
|---|---|---|---|---|
| a1b2c3d で両者が 404 で一致。以降は実装だけが d4e5f6a「refactor: unify validation (no behavior change)」で 400 に変化 | 強 | ✗ | ✓ | ✗ |
| 実装の方が新しい | 判別力なし | ✓ | ✓ | ✓ |
| テストの期待値も d4e5f6a で 404 → 400 に変更（"fix tests"） | 弱（同じ変更の一部） | ✓ | ✓ | – |
| `clients/users.py`（別の作者）は 404 を「存在しない」として扱う | 強（独立） | ✗ | ✓ | – |

判定の規則：

- **判別力のない証拠は捨てる**: すべての仮説と両立する証拠は、いくつ集めても判定を動かさない。「実装の方が新しい」「文書の方が詳しい」が典型
- **反証を探す**: 有力な仮説を支持する証拠を足すより、それを棄却しうる証拠を1つ探す方が価値が高い
- **独立性でまとめる**: 一方が他方から作られた、または同じ作業の産物である証拠は1つとして扱う（同じコミットで書かれた文書・実装・テスト、コピペ、同じ生成元）。作者・時期・作業が違えば独立として数える。どちらも Git 履歴から読んだ証拠でも、「機能追加のコミットで文書と実装が一致していた」と「後の refactor が挙動不変を名乗りつつ挙動を変えた」は別の作業なので独立である
- **明言の範囲**: 決定の記録が明言しているのは、書かれている主張だけである。明言された変更の副作用で動いた値（例：送信時刻を変えた結果、送信時刻 + 1 時間と定義された締切も動いた）には決定的な証拠が及ばない。その値は別の主張として判定する
- **決定的な証拠**: 宣言された正典（§2）、外部の権威、挙動を明言した決定の記録（挙動の変更を明言したコミット・issue・CHANGELOG、その挙動を求める ADR や障害報告の対応項目）は、強い反証がない限りそれだけで判定してよい。「挙動不変を名乗るコミットで挙動が変わっている」は強い証拠だが決定的ではない。独立した強い証拠がもう1つあれば確信度を高にできる

確信度の基準：

- **高**: 決定的な証拠がある。または独立した強い証拠が2つ以上同じ仮説を支持し、強い反証がない
- **中**: 強い証拠が1つ、または中程度の証拠が複数一致する。重要な未確認事項が残る
- **低**: 弱い証拠しかない、証拠同士が衝突する、または履歴が使えない

どの確信度でも **反転条件**（何が見つかればこの判定が覆るか）を書く。

## 7. 収束方針を決める

既定では §6 で推定した意図の側に合わせる。ただし次の3つの場合は、収束先が推定とずれうる。

- **依存**: 意図に反する挙動に誰か（特に外部）が依存している。意図どおりに直すと破壊的変更になるので、「現状を新しい正典として文書を直す」か「段階的に移行する（非推奨期間、バージョニング）」かを人間が決める
- **設計の良し悪し**: 意図された側が明らかに劣る・危険（セキュリティ、データ損失）なら、意図に戻さず判断を仰ぐ。逆に、事故で生まれた挙動の方が全体と整合し、依存もあるなら、それを新しい正典として採用する案を出してよい。設計の良し悪し（全体との整合、単純さ、安全性、運用性）を比べるのはここだけ
- **両方古い**（H-neither）: 新しい決定が必要。設計の相談として扱う（deliberate などの流儀がプロジェクトにあればそれに従う）

確信度と、修正で何が変わるかで行動を決める。

| 確信度 | 文書・コメントだけが変わる | 実行時の挙動が変わる |
|---|---|---|
| 高 | 直してよい。コミットメッセージや PR に根拠（乖離を生んだコミット等）を書く（コミットしないなら報告に書く） | 正典の挙動をテストで固定して直す。深さが慎重なら着手前に確認する |
| 中 | まだ直さない。判定と推奨を報告し、了承を得てから直す。直すときは、消える側の記述を PR の説明や issue に残す | 直さない。根拠と推奨を示して判断を仰ぐ |
| 低 | 直さない。乖離をプロジェクトの流儀（issue、TODO 等）で記録し、判断できる人と決め手になる質問を示す | 同左 |

- **依頼と判定の向きが逆のとき**: ユーザーが「文書を実装に合わせて」と頼んだのに判定は文書側が正典、のような場合は、依頼どおりには直さない。報告の冒頭で、判定が依頼の前提と逆であることと決め手を伝える。判定の向きで直してよいのは、上の表で「直してよい」に当たるもの（確信度が高く、文書・コメントだけが変わる）に限り、直したことを明示する。それ以外は確認を待つ
- **同じ根の乖離も同じ表で扱う**: 1件ずつ判定し、上の表に当てはめる。依頼が修正を含むなら、確信度が高く文書・コメントだけが変わるものは一緒に直してよい（報告に明記する）。それ以外は報告して判断を仰ぐ
- **証拠を消さない**: 確信度が高くないうちに、少数側の記述を多数側に合わせて書き換えない。文書をコードに合わせる同期は、乖離が実装の事故なら、意図の唯一の記録を消す
- **新しく書く記述で乖離を作らない**: 文書・コメントを直すときは、§1-3 で観測した実効挙動を書く。調査中に見つけた別の乖離（意図と実効挙動がずれている箇所）があれば、意図を実効挙動のように断定して覆い隠さず、ずれていることを書き分けるか、その部分には触れない。ずれを書き分けるのは別の乖離を直すことには当たらない（挙動も意図の記録も変えないので）
- **判断できる人に聞く**: 確認はまずユーザーに求める。意図の確認が要るときは、聞くべき相手（乖離を生んだコミットの作者、CODEOWNERS、文書の担当者）と、そのまま送れる質問を添える。質問は1つに絞って具体的にする（「d4e5f6a の refactor で、存在しないユーザーへの応答が 404 から 400 に変わっています。意図した変更ですか？」）
- **同じ根の乖離を探す**: 乖離を生んだコミットが他に何を変えたかを見て、同じコミットに由来する別の乖離（同じ文書の別の節、他のコメント、README）を探す。drift は群れで起きる
- **再発を防ぐ**: 同種の乖離が繰り返し起きているなら、仕組みを1行で提案する（文書をコードから生成する、契約テスト、doctest）。収束の判断がコードから読み取れない種類のものなら ADR に残す（adr skill などの流儀があればそれに従う）

## 8. 報告する

判定カードは主張ごとに1枚出す。同じ根から生じた複数の主張（例：リトライの有無・回数・待ち時間）が同じ判定になるなら1枚にまとめ、「対立」の欄で主張を分けて書いてよい。同じ根の乖離のうち判定が異なるもの、別の成果物の別の主張は、それぞれ別のカードにする（挙動に影響しない記述なら短縮版でよい）。

```markdown
### 乖離: <主張を1行で>
- **対立**: 文書「…」(`docs/api.md:42`) / 実装「…」(`src/users.py:88`) / その他の証人
- **実効挙動**: <観測した事実と、その方法>（観測 / 推測を明記）
- **類型**: drift / regression / 未実装の目標 / 最初から誤った記述（文書側の誤り）/ 初日からのバグ（実装側の誤り）/ 両方古い / 見かけの乖離
- **判定**: 意図の正典は <側>（確信度: 高 / 中 / 低）。3つ以上の成果物が関わるなら「正典: 実装とテストと CHANGELOG / ずれている側: docstring と設計書」のように側ごとに書く（同じ主張をする証人も正典側に含めてよい）
- **決め手**: <判別力のある証拠を強い順に最大3つ。SHA・path:line 付き>
- **反証・未確認**: <判定を支持しない証拠、確かめられなかったこと>
- **反転条件**: <これが見つかれば判定が覆る>
- **収束方針**: <何をどちらに合わせるか / 挙動が変わるか / 誰の判断が要るか / 乖離が今もたらしている影響（誰が困っているか）>
- **同じ根の乖離**: <同じコミットに由来し、このカードに含めなかった別の乖離（別カードへの参照）。なければ「なし」>
```

深さが軽なら、対立・判定・決め手・収束方針の4行でよい。

## アンチパターン

| 出てくる合理化 | 実態 |
|---|---|
| 動いているのだからコードが正しい | コードは今の挙動の正典であって、意図の正典ではない |
| 新しい方が正しい | 新しさは drift とも regression とも両立する。判別力がない |
| きれいな設計の方が意図だったはず | 設計の良し悪しは収束先を選ぶ基準。意図の推定に使うと隠れた制約を消す |
| 多数派に合わせればよい | 移行の途中では多数派が古い側 |
| ついでに文書をコードに合わせておこう | 報告なしの同期は、事故の唯一の証拠を消す |
| blame を見たら最終変更者は X さん | 整形・移動・一括置換が最終変更に見えているだけのことが多い |
| この文書は全体的に古い | 正典かどうかは主張ごと。古い節と正しい節が混在する |
| テストもそう書いてあるから実装が正しい | そのテストが実装と同じコミットで書き換えられていれば独立した証拠ではない |
